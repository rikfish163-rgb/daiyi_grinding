# 项目提案模板与评分标准（中文版）

说明：如何判断你的项目是否"完成"或"成功"？归根结底，这些问题取决于你在多大程度上满足了利益相关方的需求。这并不总是容易做到的，因为客户往往只是所有利益相关方中的一小部分，而且并非所有人都使用同一种语言。工程师理解的是滤波器、嵌入式系统设计、电磁物理这类概念，而客户或利益相关方可能只想要"易用"和"一次充电能用很久"的东西。仅仅理解客户真正想要什么，并开始将其转化为有效的解决方案，就不是一项小任务。高级设计课程（Senior Design）的第一个大作业就是为了完成这件事而设置的。你将在课程的前几周与客户合作，把客户的需求转化为对项目的高层工程描述。然后你将利用这份工程描述引导团队走向一个能满足客户所有需求的解决方案。

一份典范级系统提案（System Proposal）应包含以下内容：

- 执行摘要：描述项目目标以及项目为何重要

- 交付物：从客户视角描述客户想要什么

- 领域模型（Domain Model）：充分描述系统的参与者（Actors）与接口（Interfaces），以及参与者与系统之间的交互

- 利益相关方模型（Stakeholder Model）：充分描述主要利益相关方及期望的功能特性

- 系统模式模型（System Modes Model）：充分描述系统的各种运行模式，以及系统如何因各种事件的发生而切换模式

- 初始逻辑架构（Logical Architecture）：与其他模型保持一致，详细程度恰当，并体现出对项目的洞察

- 所有不同模型之间的一致性

评分将基于以下评分标准（Rubrics）：

|项目（Item）|典范（Exemplary）|合格（Adequate）|不合格（Inadequate）|
|---|---|---|---|
|标题（Title）|标题长度合理，并能体现项目的目的和/或成果|标题描述了目的和/或成果，但可以更简短或更贴切|无法从标题中看出项目的目的或成果|
|背景与引言（Background and Introduction）|对项目总体目标和项目重要性有非常清晰的描述。使用图表和参考文献来说明问题背景|总体目标可以辨认，但可以更清晰或更简洁。可以使用更多图表或参考文献来展示背景|无法辨别主要目标。没有使用图表或参考文献|
|交付物（Deliverables）|从客户视角出发，用易于理解的语言非常明确清晰地说明客户想要什么以及它将如何使用|最终成果及其使用方式需要花些力气才能辨认|不清楚最终成果是什么。语言过于技术化，外行难以理解|
|利益相关方模型（Stakeholder Model）|所有已知的利益相关方及其期望的功能特性都被考虑到。易于阅读和理解|所有主要利益相关方和期望功能特性都存在。可以更有条理或更易读|缺少一些关键利益相关方或功能特性。无法辨别必要信息|
|功能架构（Functional Architecture）|模型涵盖了所有主要参与者、输入/输出、功能和交互。标注清晰恰当、易于阅读，并与其他模型保持一致。模型足以完整描述所有利益相关方的功能特性|所有主要参与者都被考虑到了，但可以组织得更好或更易读。一致性略有欠缺。某些行为可能难以在模型中看出|缺少主要参与者、接口和/或交互。不一致或不清楚|
|交互模型（Interactions Model）|涵盖了参与者和功能特性，并恰当描述了3\-5个主要交互|仍然有用，但要么稍显复杂，要么稍显简单|缺少关键交互。过于简单或过于复杂而无法使用|

# 项目标题和封面页

与你的导师和客户合作，为项目拟定一个有意义的标题。这并不像听起来那么简单。你既要体现工作的技术细节，又不能使标题过于冗长或累赘。标题可以在全年中根据对项目的理解或范围的调整而变化。将标题放在封面页上，并附上你们的姓名、日期等。

# 项目背景与引言

为你的项目提供背景和上下文。我们需要知道你们为什么要做这个项目。它对客户和利益相关方而言为何重要？其他人在这方面做过什么（如果有的话），为什么不够？客户希望通过委托你们做这个项目实现什么？概述你们将要使用的技术。它是如何工作的？基于什么概念？涉及哪些硬件和/或软件？本节内容将用于ECE462课程最终报告的引言部分。

# 利益相关方模型

这是你们应该开发的第一个模型，必须与客户和/或其他利益相关方合作完成。该模型的目的是识别那些对项目结果有切身利益的人或人群，以及这些人或人群希望结果具备的特性。这些人或人群称为利益相关方（Stakeholders），他们希望结果具备的特性称为功能特性（Features）。

功能特性通常用带"\-性"（\-ility）或"\-能力"（\-able）后缀的词或短语来概括表达，但并不总是如此。一些常见示例有：可制造性（manufacturable）、可负担性（affordable）和可维护性（maintainable）。至少有一个功能特性必须描述项目的主要目的。

由于功能特性过于宽泛或笼统，无法直接据此设计，你需要开始将它们分解为指标（Metrics）或属性（Attributes）。在系统工程界，我们所说的属性和功能特性通常被称为利益相关方需求。创建一张表，标明哪些功能属性与指标对哪些利益相关方重要。每个指标都必须在项目开始时得到验证（Validation），并在原型开发出来后得到核实（Verification）。请记住，验证是确保该功能特性/指标/属性为适当的利益相关方增加价值；核实是确保你的解决方案能够达到该指标。你必须纳入一个基于以下每个主题的功能特性、指标、验证或核实方法：

- 其中一个或多个指标必须参照公认标准（如IEEE 802\.11）、规范（如NEC70国家电气规范）或行业规格（如PCIe）进行验证。

- 一个或多个功能特性和/或指标必须与以下更广泛的因素之一或多个相关联：公共卫生与福利、安全、全球因素、经济因素、社会因素、环境因素。

# 交互模型

交互模型（Interactions Model）从系统如何与各种参与者交互的视角来描述系统。交互应以动词加名词的形式命名，并采用相同的格式……

从一个参与者开始

描述来自该参与者的输入

描述系统应如何响应输入

描述系统向参与者输出的任何内容

开始构思交互的一种方式是设想系统的用户手册；另一种方式是使用功能架构，逐一考虑每个参与者；还有一种方式是使用如下图7所示的时序图。无论采用哪种方式，都不要忘记在这份交互清单中纳入项目的主要目的。你可能会发现，你想出了一个在功能架构中没有提供对应参与者的交互，反之亦然。这意味着你需要继续修改模型，直到达到稳定状态。最终，你的项目成功与否取决于它在多大程度上解决了利益相关方的功能特性。
