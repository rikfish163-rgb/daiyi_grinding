# 校企合作各阶段项目报告体系

**页面定位**：本页面向项目组全体成员与校企双方，说明一个校企合作项目从立项到结项需要签订和归档的项目报告体系。

**依据**：云盘「项目报告体系参考文档」文件夹（[H6b0fbC3Nl8IeidTFuQckId4nnc](https://hustdian.feishu.cn/drive/folder/H6b0fbC3Nl8IeidTFuQckId4nnc)）中的 7 份参考文档，来自美国罗斯豪曼大学ECE 高年级课程设计项目（MATHCOUNTS 抢答器系统，Team 13），完整覆盖"提案 → 计划 → 设计 → 测试 → 结项"五个阶段。

**关键点**：**项目提案需甲方公司与项目组双方签字**；后续每个阶段文档在上阶段成果基础上细化，环环相扣、可追溯。

# 总体框架

校企合作项目按"立项 → 规划 → 设计 → 验证 → 结项"五个阶段推进，每一阶段对应一份正式项目报告。五份报告构成完整证据链：提案锁定"做什么、为何做"（双方签字），计划锁定"谁来做、何时做"，系统要求与内部设计锁定"做成什么样、怎么做"，测试报告锁定"如何证明做对了"，完成报告锁定"最终交付了什么、结果如何"。

|阶段|对应报告|核心作用|
|---|---|---|
|① 立项|项目提案（System Proposal）|界定项目范围与交付物，**甲方公司与项目组双方签字**，是合作的法律与范围基准|
|② 规划|项目计划（Project Plan）|拆解里程碑、任务分工、时间表、预算与培训计划，回答"怎么落地"|
|③ 设计|系统要求和内部设计（System Specification \& Decomposition）|先写甲方视角的规格说明，再做团队内部的系统分解与设计决策|
|④ 验证|测试方案的测试报告（Test Plan \& Report）|把需求翻译为可量化测试项，用数据证明系统满足要求|
|⑤ 结项|项目完成报告（Final Report）|汇总全部成果、验证结论、预算与经验，正式向甲方移交|

# ① 项目提案（需双方签字）

## 定位

项目提案是项目启动后的第一份正式文档，也是唯一一份**必须由甲方（客户）与项目组（乙方）签字**的协议性文件。它把甲方口头的、零散的诉求翻译成工程团队可执行的高层描述，作为判断"项目是否完成、是否成功"的基准。

## 必须包含的内容

- **项目背景与引言**：为什么做这个项目，对甲方与干系人为何重要，现有方案存在什么不足，甲方希望通过本项目达成什么目标，涉及哪些技术。

- **项目交付物**：从甲方视角、用非技术语言描述项目结束时交到甲方手里的实物成果（如"一套可运行的控制器与按钮盒"），越具体越好；若甲方额外要求说明书等文档，也应列入。

- **干系人模型（Stakeholder Model）**：识别对项目结果有切身利益的人群，以及他们期望的**特性（Features）**——通常用"\-ility/\-able"结尾的词汇表达（如 affordable 经济、durable 耐用、intuitive 直观、transportable 便携）。至少一个特性须描述项目的主要目的。

- **特性分解为指标（Metrics）**：把宽泛的特性拆成可量化、可验证的需求，如"整机成本低于200美元""按下按钮后LED在20ms内点亮"。每个指标须同时给出**验证（Validation）**——为什么这个指标对干系人有价值，以及**核实（Verification）**——原型完成后如何测试证明达标。

- **黑盒模型**：定义系统边界，用一张图加一张表说明系统与各参与者（Actor）及输入/输出（I/O）的关系；参与者数量控制在10个以内，功能块不超过10个。

- **交互模型（Interactions Model）**：从"参与者发起动作 → 系统如何响应"的角度描述系统行为，覆盖项目的主要用途。

- **预算与采购计划**：初步成本估算（单位成本 \+ 开发成本），说明零件采购渠道与结算方式。

- **签名与协议页**：**甲方（Client）、项目负责人（Supervisor）与全体项目组成员签字**。签字即表示甲方认可项目组对范围与交付物的理解；范围、指标或交付物的重大变更须重新签字确认，微小说明性修订不需重新签字。

**对本项目的启示**：10/8 组会上宋建建提出的"提案定量化"与黑晓军推进的"合同\+技术指标文档"，正对应本阶段。项目提案应写明：甲方（戴屹）当前的生产状态与痛点、要达成的定量目标（如打磨精度、粗糙度、节拍）、成本与周期，并**由戴屹公司与项目组双方签字确认**，作为后续验收依据。

# ② 项目计划

## 定位

项目计划在提案批准后编写，把"做什么"细化成"谁来做、何时做完、花多少钱"，是项目执行的行动指南。

## 必须包含的内容

- **执行摘要**：一段话概括项目目标、系统构成与关键约束，与提案保持一致。

- **里程碑与时间表（Timeline \& Milestones）**：把项目拆成若干里程碑，每个里程碑写明：完成什么（Description）、由谁/如何核实完成（Verified by）、截止日期（Date of Comp）。参考文档的里程碑示例：全部零件选定并下单 → 面包板实现基础抢答功能 → 加入计时器功能 → 面包板实现完整功能 → PCB 制作 → 3D 打印外壳 → 最终完成。

- **任务分工（Division of Labor）**：为每位成员分配明确职责；说明哪些任务可并行、各里程碑存在哪些瓶颈（Roadblocks/Bottlenecks）及应对方案。

- **培训计划（Training Plan）**：列出完成项目所需的技能清单，逐人说明其现有技能与需要补充学习的内容及截止时间。

- **资源与预算**：逐里程碑列出所需物料清单（BOM）与估算成本，区分**单位成本**（最终产品用料）与**开发成本**（试验、损耗、废弃件等）。

# ③ 系统要求和内部设计

## 定位

该阶段包含两份配套文档，先对外、后对内，从"系统应该满足什么"推进到"系统内部如何实现"。

## 3\.1 系统要求/规格说明（System Specification）

**面向甲方**，用工程语言固化系统行为与约束，是提案中指标的权威细化，也是后续设计与测试的共同基准。

- **总体描述**：系统由哪些部分组成（如中央控制器 \+ 若干远程按钮盒 \+ 计时显示），整体如何工作。

- **设备描述**：逐部件说明物理形态、功能与操作方式（如控制器的外壳、按钮、开关、接口、电源；按钮盒的按键、指示灯、线缆）。

- **操作说明（Description of Operation）**：按时间顺序描述从初始设置到每轮答题的完整操作流程，包括各按钮的响应行为。

## 3\.2 内部设计/系统分解（System Decomposition）

**面向开发团队**，在规格基础上做内部架构与实现设计。

- **执行摘要**：重申项目目标与系统总体方案。

- **技术需求表**：把每条需求编号（如 E\-1、A\-1、D\-1、F\-1……），逐条给出：需求内容、验证理由（Validation）、核实方法（Verification）、为可测性而做的设计安排（Design for Test）。

- **分层设计描述**：  

    - 总体系统框图（硬件 \+ 软件两个子系统的关系）；

    - 软件设计：用状态机描述系统各运行状态与状态迁移（如"初始停止 → 计时运行 → 计时归零"），覆盖按钮、队列、模式切换等全部行为；

    - 硬件设计：黑盒模型 → 整机原理图 → 分模块原理图（如按钮盒、主控制器、计时单元、LED驱动电路）。

- **设计决策论证（Decision Justification）**：对关键选型（如主控芯片）列出候选方案，按成本、引脚数、尺寸、团队熟悉度、功能支持等维度对比，说明最终选择及其理由。

# ④ 测试方案的测试报告

## 定位

测试计划在实现阶段编写、在原型完成后执行，最终形成测试报告，用**数据**逐条证明系统满足系统要求中的指标。参考文档中，测试计划与测试报告合并在同一份文档（Test Plan \& Report）：先写明测试方案，再给出执行后的数据、分析与结论。

## 必须包含的内容

- **背景**：说明本次测试要验证哪些需求、为什么这些需求重要。

- **待验证需求清单**：列出需求编号、需求原文与验证目的（对应系统分解中的需求编号，如 B\-2、F\-5、F\-6）。

- **设备与工具**：列出测试所需的全部仪器与器材（如示波器、电源、被测单元、线缆）。

- **测试步骤（Procedure）**：把每个测试目标写成可重复执行的逐步操作，明确通过判据（Pass Criterion），如"时间差小于 20ms 即通过""30/30 全部通过"。

- **数据采集与分析**：记录原始数据（如示波器截图、逐轮测试的 Pass/Fail 表），并做统计汇总。

- **结论**：逐条给出每个需求的最终判定（通过/不通过）、余量（如"实测 11ms，比 20ms 要求余量 9ms"）与说明。

**对本项目的启示**：具身打磨项目的验收指标（打磨精度、表面粗糙度、节拍等）应同样拆成可量化测试项，提前规划测试设备（如三维扫描仪精度测量、力控数据采集、节拍计时）与通过判据，避免"甲方说你没做完、你说做完了"的扯皮。

# ⑤ 项目完成报告

## 定位

项目完成报告是结项阶段的总结性文档，向甲方与评审方完整交代"做了什么、做得怎么样、花了多少钱、有什么经验教训"，也是项目归档与移交的核心文件。

## 必须包含的内容

- **封面与致送**：项目名称、致送方（甲方与指导教师）、提交方（项目组全体成员）、版本与日期。

- **执行摘要**：概述项目背景、系统构成、主要成果与总体结论（含与既有方案的对比）。

- **介绍与项目概述**：项目背景、干系人、交付物、特性与规格、结论，可直接复用/完善提案与设计阶段内容。

- **成果（Accomplishments）**：逐模块介绍设计与实现（如控制器电路、PCB、外壳、软件实现、蓝牙 GUI 等），附用户指南。

- **需求验证（Verification of Requirements）**：对关键需求逐条给出验证过程与结果数据（对应测试报告结论）。

- **项目计划与时间线**：计划时间线 vs 实际时间线的对照，说明延期原因。

- **预算**：最终实际支出与预算的对照。

- **建议与后续工作（Recommendations / Going Further）**：对甲方的使用建议、可继续改进的方向。

- **影响分析**：项目对公共健康与安全、全球/社会/经济/环境等更广泛议题的影响；系统失效模式分析。

- **参考文献与附录**：规范引用（如 I2C、RJ45/T568B 标准），附录包含用户指南等交付性文档。

# 五阶段关系与流转规则

- **逐级细化**：每份文档以上一阶段成果为输入——提案产出特性与指标 → 计划细化执行 → 规格固化指标 → 测试逐条验证指标 → 报告汇总全部证据。

- **需求编号贯穿**：从系统分解起，每条需求有唯一编号（如 F\-5）；测试报告与完成报告按同一编号引用，保证"需求—测试—结论"可追溯。

- **变更管理**：范围、指标、交付物的重大变更须更新提案并经双方重新签字；计划、设计层面的调整在对应文档中修订并保留版本。

- **签字节点**：至少两处硬性签字——项目提案（甲方 \+ 项目组双方）；最终交付时建议由甲方签署验收确认（对应完成报告）。
