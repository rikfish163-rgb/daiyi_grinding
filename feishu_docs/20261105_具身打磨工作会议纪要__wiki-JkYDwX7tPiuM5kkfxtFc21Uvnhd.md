# 数据采集设备情况

## 结构与采集流程

- **相机与量程**：搭载一台已完成标定的 3D 相机，设计图框出的范围即相机测量范围。

- **转台**：相机下方设转台，可 360 度连续旋转，带动工件转动。

- **采集原理**：单次拍摄只能覆盖部分表面，因此把工件放到转台的不同角度分别拍摄，采到一周点云后做**点云拼接**，得到完整工件点云。

- **后续处理**：拼接后的点云放到已发来的服务器上处理。

- **控制方式**：随设备发来一张运动控制卡，插到工作站，用网线连接电箱内的伺服驱动器即可驱动转台。

## 薛力源：3D\-ADAM 工业异常数据集调研

**本周完成**：阅读 ICRA2026 的一篇论文，其提出 3D\-ADAM 大规模工业 3D 异常数据集。

- **数据规模**：高分辨率扫描 1 万多次，覆盖 217 个独立零件、28 个物体类别，标注 27000 多个缺陷实例，区分 12 类缺陷与 16 类机械结构。

- **采集与标注**：多传感器、多视角采集，配合专家验证。

- **与项目的相似性**：数据集中的毛刺、粗糙、飞边，与本项目铸件的飞边、毛刺、浇口残根在几何上具有相似性，其采集与标注方法可作为自建数据集的参考。

- **直接启发**：针对打磨任务的百万级点云处理与微小缺陷识别需求，可以该数据集为范例，研究不同降采样方法对细节保留与检测精度的影响。

**下一步**：追溯使用该数据集的论文，学习其检测模型与检测方法，并尝试迁移到打磨任务；相机到位后尽快完成数据集采集，先上手工业相机的应用。

**企业方回应**：易昌表示暂无补充，“因为现在我们真正的实际实验还没开始，后面等设备到了我这边会过来”。

## 孔凌峰：工作站训练环境与分割实验

**本周完成**：拿到工作站后完成某网络训练的初始环境配置；接着上周介绍的论文（陶瓷封装基板表面缺陷分割任务与数据集）做进一步实验，并对比本机（显存较小）与工作站的训练开销。

- **结论一**：工作站显存更大，可以用更大的 batch size、提升数据集覆盖率，从而在相同时间达到更好的训练效果。

- **结论二**：PTV3 网络在本机跑不起来，在工作站上可以有效运行，效果比 PointNet\+\+ 略好。

- **结论三（问题）**：这一系列实验的**准确率仍明显偏低**，需要在点云处理方式、网络结构、训练配置上继续优化。

**下一步**：注意规模差异——论文数据集总量约 1\.8 亿点，但单件点云约数十万点，而项目部分工件点云可能达到百万数量级，因此要调整**分块尺寸与训练覆盖方式**，既保留飞边与毛刺信息，又不超出实际显存。相机到位后扫描真实工件，统计点数、局部点间距、缺失点与重复点，人工确认毛刺根部是否被实际扫描到；随后建立工件整件的检测基线，跑通“分块预测—还原”流程，并加入飞边区域召回率、漏检与误报区域数、根部定位误差等工件级指标。

## 王释钰：仿真场景与轨迹生成系统

**本周完成**：依据两份文档把实验场地场景与机械臂参数在 ROS 仿真系统中搭建出来，并在该环境上搭建“指定加工区域→输出打磨轨迹”的系统。

**系统架构**：网页端选择工件、上传点云（当前尚无缺陷识别模块，使用已标注缺陷区域的数据集）→ 生成工件表面路径 → 机械臂运动规划（可能失败）→ 碰撞检查与自动修正 → 用 ROS 回放通过的轨迹。修正手段包括更换模具候选、调整法向方向、更换阈值、初值与分支等；未通过的片段会给出原因，包括姿态达不到、机械臂碰撞、模具与工件干涉、安全距离不够、尝试时间用完。

**存在问题**：18 段轨迹中只通过 1 段，**轨迹自动修正效果较差**；生成步骤复杂、速度偏慢；因部分参数不明确，进刀、退刀、转场等提示目前仍属演示性质。

**下一步**：优化轨迹自动修正模块、提升生成速度、接入打磨工具与转换器数据（铣刀、钢刷、磨轮）。

**现场追问**：王释钰问三脚架部分能否转动，易昌答“这个能转”。

# 存在问题与技术路线讨论

## 仿真结果缺真机校验

黑晓军指出，王释钰这套系统是借助 AI 工具、依据前期准备的实验台描述与图片导入仿真工具搭建的，“看上去是模是样的”，但**精度到底有多少还不确定，需要给出具体测试用例**。他请易昌给建议：怎么检测仿真器的结果是不是准的？

易昌答得很直接：“这个可能只有在实际上工件去测试了。”黑晓军接受这一结论并顺势定下路线——**最终要回到物理世界**：把真实工件、几何尺寸与三维数字模型导入仿真器，用物理世界的测量结果与仿真结果对标，这一步“很关键”。

为支撑这条路线，易昌确认设计模型与实际系统**一模一样**，可以把转台等整个物理场景的几何尺寸与数字模型一并提供。

## 准确率：工程可用性的标尺尚未建立

黑晓军请易昌介绍此前做点云工作时测得的指标。易昌说明当时做法比较简单，**没有用神经网络，直接用矩阵运算处理点云**。黑晓军据此判断当前准确率偏低，但反过来也意味着创新空间很大，于是追问“一般来讲，准确率要到多少才可用，在工程上能够用”。

|参照对象|做法与结果|对本项目的意义|
|---|---|---|
|企业方传统方法|未用点云做缺陷识别，只用点云测量工件、与三维模型比对，去掉多余部分|说明工程侧没有现成的识别指标可循|
|论文方法|该场景准确率约 70% 到 90% 多，评价为识别异常区域与真实异常区域的交并比|给出数量级参照，但场景差异大，不能直接对标|
|本项目现状|直接照搬论文方法的初步实验，准确率明显偏低|需要针对自有场景重做处理方式与训练配置|

黑晓军进一步追问：实际场景里要做到什么程度算达标？易昌认为**人工介入可能更好**——自主识别之后由人工检查，把不对的地方直接圈出来，“这个是我们后面做软件的时候，需要添加的内容”。黑晓军则提出分阶段思路：这一期先把整个流程走通、建立初步基准，并请易昌考虑“未来这两个月我们到底能做到什么程度”，给出一个可行的目标；易昌答复“我后面考虑一下”。

## 数据闭环与规模适配

会议实际确立了一条完整的链路：**相机\+转台采集 → 点云拼接 → 服务器处理 → 数据集构建 → 模型训练与检测 → 真机路径验证**。每一环都已被具体化：采集侧的标定、转台角度与拼接；数据侧的点数、点间距、重复点、毛刺根部是否采到；训练侧的分块尺寸、显存约束与覆盖率；验证侧的整段路径与工件级指标。

## 共享与协作机制

系统选型未定，但先立规矩：环境必须标注。这条规矩的意义在于——只有把每位同学的操作系统、软件与版本记录清楚，才能反过来判断换系统会不会导致重写，也才能决定共享主机最终采用 Linux 分时还是 Windows 独占。
