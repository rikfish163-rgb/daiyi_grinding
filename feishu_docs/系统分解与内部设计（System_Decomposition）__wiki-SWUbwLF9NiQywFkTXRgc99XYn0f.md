# Executive Summary

The nationwide middle school\-level competition MATHCOUNTS has been held for the last several decades, often at Rose\-Hulman Institute of Technology, yet the hardware behind its buzzer system has not been changed in all that time\. As such, our goal for this project is to redesign this system to last at least 10 years, be much easier to operate, and maintain the levels of functionality and ease of use expected of such a system\. In the final “Countdown Round” of MATHCOUNTS, 2\-6 competitors are presented with a question and given 20\-60 seconds to answer\. Every competitor is provided with a button unit that is wired to a center console which resides in front of the competition operator\. The first competitor to buzz in responds to the question and, depending on the rules, either the second student to buzz in is allowed to answer or the rest of the students get another chance to buzz in\. Only the first buzzer pressed triggers a light and sound\. The competition operator can go to the next competitor who buzzed in, reset the button units, switch between operating modes, and manage the timers\.  A small timer will sit on the center console in sight of the competition operator and a larger one will face the competitors\. Both timers will display the same time and be controlled by the competition operator\. The competition operator manages the timers by starting, resetting, or changing the length of time that will be displayed \(as long as the timer isn’t currently ticking down\)\.

The redesigned system will use an Arduino microcontroller interfacing with 6 button units, 2 timer displays, and a set of button inputs on the center console\. There will be two modes of the system set with a switch on the controller: Type 1 Mode \(reset boxes\) and Type 2 Mode \(next answer\)\. In Type 1 Mode, when a competitor presses their button first the operator will reset all buzzers, and if the answer is wrong, any competitor can buzz in again with a different answer\. In Type 2 Mode, the system remembers the order of all the buttons pressed, so when a competitor answers incorrectly, the operator can press the “Next Answer” button to go to the next competitor who buzzed in\. These two features will be operated by the same physical button, but its effect will change by flipping the “Change Mode” switch\. In both modes, the timer will not stop when a competitor buzzes in\. Additionally, by using “Timer Up” and “Timer Down” buttons, the length of the timespan of the timer can be changed by 5\-second increments, from 20 seconds to 60 seconds\.

# Hierarchical Descriptions

## IV\.1 Overall System Depiction

Figure 1: Higher\-Level Diagram of Hardware and Software

Shown in Figure 1 is the higher\-level diagram of the overall buzzer system\. There will both be a hardware and software side of the development process\. Both will have their own subsystems that will have to be developed for the entire buzzer system to work\. The hardware of the system includes a timer unit, push button boxes including a push button and LED, and a main control unit containing the microcontroller, power supply, and a buzzer\. It additionally uses I/O connections between the main control unit and both the timer unit and push\-button boxes, and PCBs in the timer unit, push\-button boxes, and main control unit\. The software will be driven by a state machine, while also featuring a timer and pin extenders that use I2C\.

## IV\.2 High\-Level Software Descriptions

Figure 2: State Machine of Basic Operations

Figure 2 depicts a state machine describing the basic operations of the system: pressing buttons, having buttons be stored in the next answer queue when another contestant’s LED has already lit up, and switching between operational states\. As was shown in Figure 3, the system is initialized in the “stopped at initial time” state, which is also achieved by pressing the “Reset Timer” button \(which can be pressed at any time to bring the system to this state\)\. No matter how this state is reached, when the system arrives, the next answer queue will be cleared, and all button box LEDs will be turned off\. Pressing “Start Timer” while in this state will first check the “Change Mode” switch’s position in order to determine which mode the system will operate in \(see Figure 5 below for a more zoomed\-in view of this\), then move on to the “timer running” state, at which point the timer will tick down from its initial time \(see Figure 4 to see how this is set\) to 0\.

While in the running state, pressing the button on any button box will be registered \(again, it is possible to do this outside of this state, but it will have no effect\)\. If that button is pressed when no other button box’s LED is on, it will result in that box’s LED turning on and the first button noise to sound out of the buzzer in the center console\. If the button is pressed and another button box’s LED is already on, then the next step in the operation depends on two factors: the mode and the queue\. If the mode is Type 1, nothing more will happen, and the timer will continue running\. If the mode is Type 2 but that button box is already in the next answer queue \(i\.e\., that contestant has already buzzed in for this “round”\), nothing will happen, and the timer will continue running\. Finally, if both the system is in Type 2 mode and the button box has not already been added into the queue, it will be added to the end of the queue before the system, again, returns to the “timer running” state\.

Once the timer reaches 0, button inputs will no longer be accepted \(although LEDs will not turn off until the “Reset Timer” button is pressed\. The only way to exit this state is to press “Reset Timer” and return to the “stopped at initial time” state\. Additionally, when the “stopped at 0” state is first reached, a unique sound will play out of the buzzer in the center console\.

Figure 3: Initialization State Machine

Depicted in Figure 3 is a representation of the initialization of the system in the form of a state machine \(in order to be in line with other diagrams, even though a state machine for a fixed, linear process is somewhat pointless\)\. As is shown, when the system is first turned on the next answer queue will be empty, the initial mode is set to Type 1, the initial length of the timer is set to 20s, and the system is kept in the “stopped at initial time” state\.

Figure 4: State Diagram Describing Timer Length Adjustment

Depicted in Figure 4, above, is the state machine describing the timer length change functionality of the system\. As is shown, as well as described elsewhere, the timer length, which is the length of time the timer resets to after the “Reset Timer” button is pressed and runs for after the “Start Timer” button is pressed\. This begins at 20 seconds and can be increased in increments of 5 by pressing the “Timer Up” button or decreased in increments of 5 by pressing the “Timer Down” button\. The maximum length is 60s and the minimum is 20s\. As is shown in the state diagram, changing the timer length is only allowed in the “stopped at initial time” state—in other words, it cannot be changed while the timer is running, nor when it is stopped after reaching 0\. This state is reached both upon initial boot\-up of the system, as well as after pressing the “Reset Timer” button\.

Figure 5: Mode Change State Machine

Depicted in Figure 5 is the state machine depicting the switching between the two modes of operation for the system: Type 1 and Type 2\. As is shown, this switch occurs when transitioning between the “stopped at initial time” and “timer running” states, and the mode is set based on the position of the “Change Mode” switch\. Of course, the switch can be flipped at any time, but its state will not be read until this transition is reached\. In order to change mode again, it is necessary to reset the system to return to the “stopped at initial time” state\.

Figure 6: Next Answer State Machine

Figure 6 depicts the state machine for the Type 1 and Type 2 modes of the system\. As can be seen in the state machine, pressing “Next Answer” only has an effect when in the “timer running” state\. When in Type 1 mode, pressing “Next Answer” causes all Box LEDs to turn off, allowing contestants to buzz in once again, before returning to the “timer running” state\. Type 2 mode is more involved; when “Next Answer” is pressed in this mode, the system will check the next value in the next answer queue\. If the queue is empty, or if the index has reached the end of the queue, this button functions as it does in Type 1 mode: turning off all LEDs before returning to the “timer running” state\. On the other hand, if there is another box in the queue, the LED of the current box turns off while the LED of that next box turns on, accompanied by the second buzz\-in sound being played from the buzzer in the current system\. The index in the queue will also move forward, as opposed to removing the previously\-lit\-up box from the queue, in order to ensure that a contestant can’t join the queue for a question twice before it has been cleared\.

## IV\.4 Mid\-Level Hardware Descriptions

Figure 9: Button Box Schematic

This figure shows an implementation for one of the six button boxes that will be part of the entire unit\. Each button box will use an ethernet port to communicate with the central controller and makes use of the circuit described in Figure 12 for the LED implementation\. A button is used to gather inputs from each box, and a single output pin from the microcontroller is used to drive a transistor that acts as a switch for the LED which must draw power from the provided 5V line and then directed through each of 6 LEDs in parallel\. Since this unit only has 2 lines for communication, a communication protocol is not necessary, and the inputs and outputs can be carried directly over ethernet\.

Figure 10: Main Controller Schematic

The main controller above acts as the main hub for the device, collecting the inputs over ethernet from the button boxes, and directly from the control setting buttons\. It then uses a PWM pin to generate noise via an attached buzzer and uses I2C communication to interface with two pin extender units which control the external timer module, as well as a timer that is built into the main controller\.

Figure 11: Timer Units

The external timer unit, and control timer unit \(part of the main controller\) use a MCP23017 pin extender to allow for the control of the seven segment displays\. They communicate via I2C with the main microcontroller and have addresses that can be hard wired in to allow for many additional units\. The timer unit uses an ethernet cable to connect with the main microcontroller while the main controller’s timer will be connected directly on a PCB\. These displays require a much higher voltage than the rest of the system, so a 9v connection will be included, but the specifics of routing that power through the seven segment displays has not yet been decided on\.

Figure 12: Circuit for Lighting LED

The microcontroller was unable to supply enough current to the LED to make it sufficiently bright\. Therefore, the circuit shown in Figure 12 was used to amplify the output current\. The circuit shown is a mostly standard common emitter amplifier\.  When the pin is set to 0 V, then current flows into the base of the BJT and turns on the LED\. When the pin is set to 3\.3 V, the current is dramatically reduced\. The diode was added to act as a voltage drop from the rail, since the LED would not fully turn off when the pin was set to 3\.3 V\. The diode reduces the base voltage of the BJT and therefore reduces the current\. This dramatically reduces the current in the off state while leaving the on state relatively unaffected\.

# Decision Justification

Context:

After deciding to use a microcontroller to run the system, the team had to decide which microcontroller to use\. There are many microcontroller options available, but one needed to be selected\. Also, the team has decided that the most important criteria for selecting which microcontroller would be the best would be using the number of GPIO pins, cost, size, whether it supports interrupts, and how familiar with the microcontroller the team is\. We chose these as the most important features as they all line up with the system requirements the most\. The microcontroller needs a lot of GPIO pins to connect to all the different components in the system such as a seven\-segment display\. A microcontroller that is smaller and cheaper is better for the requirements of the system being under budget and being transportable\. The microcontroller also needs to be able to handle interrupts for when any of the pushbutton\-boxes get pushed\. Other features of the microcontroller are less important because they don’t apply to as many features\. As described above there are many things we need from our microcontroller, and every controller has both pros and cons\. The Arduino is easier to use, but more expensive\. The Raspberry Pi is noticeably cheaper, but more difficult to set up\. By contrast, the Bluefruit is both more expensive and more limited in terms of pins but was instead designed to be easily compatible with Bluetooth, came with an inbuilt speaker and set of customizable LEDS, and was compatible with a preexisting buzzer system we as a team were considering basing our system on\. The controllers also have small variances in things like GPIO pins and size\.

Design Decision Justification:

The team has decided to use Option 1\. Option 3 was designed primarily to work alongside the preexisting Adafruit\-created buzzer system that the team were initially considering basing the system from\. The idea was to take the existing project, implement it \(which would get rid of most of the issues stemming from our unfamiliarity with this specific microcontroller\), then modify it to meet the specific requirements of our clients, such as having up to six contestants and including a timer unit\.
